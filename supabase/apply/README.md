# Apply the upgrade migrations on hosted Supabase (owner, no Docker)

You chose to run the schema changes through the Supabase web SQL editor instead of
a local Docker stack. This folder is set up for exactly that.

## 1. Open the SQL editor

<https://supabase.com/dashboard/project/njlzgfddfnnqujaodbta/sql/new>

## 2. Paste and run the bundle

Paste the whole of

```
supabase/apply/apply-all-upgrade-migrations.sql
```

into the editor and press **Run**. That file is generated by
`scripts/build-migration-bundle.mjs`, which concatenates every new upgrade
migration in timestamp order with the correct file boundaries marked, so the
editor runs them as one transaction-like script.

It is written to be **safe to re-run**: every statement is either
`if not exists` / `drop ... if exists`, or an idempotent `update`/`delete` whose
predicate cannot match a row that a previous run already changed.

## 3. What it changes

Read the header of each migration for the reasoning. In outline:

| Migration | Effect |
|---|---|
| `20261010000000_product_points_names.sql` | Sets `points_name_en`/`_ar` on 14 game products so 425 bare supplier denominations ("55", "330") render as "55 Diamonds". Already applied. |
| `20261010000001_delete_rejected_test_recharges.sql` | Deletes 11 owner test recharge attempts and their 10 dead `expired` Sam invoices. Already applied. |
| `20261010010000_order_hold_state.sql` | Adds `held` to the `orders.status` constraint plus `held_reason` / `held_at`. |
| `20261010030000_batstore_stock_sync.sql` | Storage and indexes for the scheduled BatStore stock sync. |
| `20261010090000_customer_telegram_channel.sql` | Customer Telegram broadcast records. |
| `20261010100000_coupons.sql` | `coupons` and `coupon_redemptions`. |
| `20261010110000_referral_loop.sql` | Referral codes and credit ledger. |

The two `2026101000000*` files are already live (applied through the Supabase
REST API); re-running them is a no-op.

## 4. Verify

Each migration ends with a comment block listing the verification queries to run.
The quick version, paste after the bundle:

```sql
select status, count(*) from public.orders group by status order by status;
select column_name from information_schema.columns
 where table_schema='public' and table_name='orders' and column_name in ('held_reason','held_at');
select pg_get_constraintdef(oid) from pg_constraint
 where conrelid='public.orders'::regclass and conname='orders_status_check';
select status, count(*) from public.recharge_requests group by status order by status;
select count(*) from public.offers o join public.products p on p.id=o.product_id
 where o.is_active and o.name_en ~ '^[0-9]+$' and coalesce(p.points_name_en,'')='';
```

Expected: `held_reason`/`held_at` present, the constraint definition mentions
`held`, `rejected = 2`, and the last query returns `0`.

## 5. Why not `supabase db push`

Three migrations dated `20260911` are absent from remote migration history.
A plain `db push` will offer to insert them, and the missing-offers one invents
prices. Never run `db push --include-all` against this project. Applying the
reviewed files through the SQL editor leaves migration history untouched, which
is the behaviour this upgrade wants.

## 6. Do not forget the code deploy

These migrations add schema the new code expects. The dashboard features (held
queue, coupons, referrals, Telegram broadcast) only appear after the storefront
is deployed from this working tree. Applying SQL alone changes nothing visible.
